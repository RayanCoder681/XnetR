Le problème

Un système fiable, mais fermé

Le dashboard manager fonctionne bien pour un usage manuel — mais il bloque toute automatisation ou intégration classique.

Sans XnetR

Chaque activation demande une action manuelle : connexion, recherche de l'utilisateur, sélection du profil, clic de validation. Répété des dizaines de fois par jour, sujet à l'erreur humaine, impossible à tracer finement.

Avec XnetR

Une seule requête — activatePackage(username, profile, quantity) — déclenche tout le parcours, exécuté par un moteur d'automatisation, journalisé de bout en bout.

Fonctionnement

Le même parcours qu'un manager, sans le manager

Cinq étapes séquentielles, reproduites fidèlement par le moteur d'automatisation, une activation à la fois.

01

Connexion

Ouverture d'une session manager sécurisée et persistée.

02

Recherche

Localisation du compte utilisateur cible dans le dashboard.

03

Sélection

Choix du profil Internet et de la quantité à activer.

04

Activation

Validation de l'activation dans l'interface existante.

05

Confirmation

Lecture du résultat et journalisation complète.

Architecture

API et automatisation, strictement séparées

Le backend ne pilote jamais Playwright directement : il délègue à un worker isolé via une file d'attente, pour ne jamais bloquer l'API sur une session navigateur.

Sécurité

Zéro identifiant exposé, tout journalisé

Le système est conçu pour un usage en production, avec les mêmes exigences que le dashboard qu'il pilote.

Secrets chiffrés

Identifiants manager chiffrés (AES-256) via un gestionnaire de secrets, jamais en clair dans le code ou les logs.

Rotation des sessions

Re-authentification automatique en cas d'expiration, sans intervention manuelle.

Journalisation complète

Chaque action sur le dashboard existant est tracée : étape, horodatage, résultat.

Aucune modification du système

Interaction exclusivement via l'interface graphique existante, jamais d'accès direct à sa base de données.
